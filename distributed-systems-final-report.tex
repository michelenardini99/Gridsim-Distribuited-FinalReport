\begin{abstract}
GridSim-Distribuited simulates a small electrical grid --- houses, solar panels, batteries and
the cables connecting them --- as a genuinely distributed, tick-driven system rather than as a
single-process program. On the backend, every grid entity and every running simulation is an
independent, event-sourced Apache Pekko actor: cluster sharding gives each one a stable identity
regardless of which node currently hosts it, and Pekko Persistence lets it recover its exact state
by replaying its event log. Because that log is kept in a Redis store shared by every backend
node, rather than inside the node that hosts the actor, a simulation survives not only an actor
restart but also the crash of a whole node, resuming on a surviving one. Each simulated tick is a scatter/gather exchange
between a simulation's orchestrating actor and its entities, guarded by a timeout; a timed-out
tick is retried with exponential backoff, the retry is idempotent with respect to the
at-least-once delivery a distributed system has to assume, and a run of repeated failures is
reported to clients as a degraded status rather than silently retried forever. A Split Brain
Resolver, configured with a keep-majority strategy, gives the cluster a deterministic response to
a network partition. A separate ScalaFX desktop client, structured with an MVVM architecture,
drives the simulation's lifecycle through a synchronous HTTP API and observes its progress through
Protobuf-encoded telemetry published over Apache Kafka, a channel that lets several GUI instances
watch the same simulation at once without the backend tracking who is listening. Grid topologies
are authored through a small internal Scala DSL with accumulating validation, from which the
system's four built-in scenario presets are built. This report documents the requirements,
architecture, implementation and validation of the system.
\end{abstract}

\chapter{Concept}\label{concept}

\section{Type of product}

GridSim is a distributed desktop application for energy micro-grid simulation, composed of
a backend simulation engine and a graphical client, which can be deployed either as a
single co-located process or as two independent, network-connected components.

More precisely, the product is a hybrid of two of the categories listed above:
\begin{itemize}
    \item A \textbf{desktop application} with a graphical user interface (GUI), built with ScalaFX,
  through which the user creates micro-grid scenarios, starts/pauses/steps the simulation,
  and visualizes its evolution as an interactive, real-time graph (nodes = energy entities,
  edges = cables), together with dashboards and per-element detail panels (battery state of
  charge, solar panel irradiance, instantaneous power flow on a cable, etc.).
  \item A \textbf{backend service}, built on top of an actor system (Apache Pekko), that
  hosts the actual simulation engine, exposes an HTTP REST API to create/control simulations
  remotely, and publishes simulation telemetry on Apache Kafka topics so that one or more GUI
  clients can subscribe to the live state of a simulation without being co-located with the
  engine that computes it.
\end{itemize}

The two parts always run as separate processes: a headless backend node (or cluster of
nodes) running the simulation, and one or more GUI clients connecting to it via HTTP (control
plane) and Kafka (data plane), either on the same machine or from a different one. A Launcher
component selects at startup which process to run: a single-node backend for local
development, a clustered backend replica, or the GUI.

In addition to the interactive product, the project also provides a small embedded Domain
Specific Language (DSL), written in Scala, used to declaratively describe a micro-grid
scenario (houses, solar panels, batteries, cables, external grid, weather profile).

\section{Use case}

GridSim models a local energy micro-grid as a directed graph: nodes are energy entities
(houses, standalone solar panels, battery storages, and a single "External Grid" node
acting as an infinite source/sink), and edges are cables with a maximum power-transport
capacity. The simulation advances in discrete time steps ("ticks"); at every tick the
environment is updated, each entity resolves
its local energy balance (e.g., a house nets its consumption against its own solar
production and battery), and the residual surplus/deficit is routed through the micro-grid
topology using a power-flow algorithm, ultimately settling any
unbalanced energy with the External Grid. All intermediate states are kept immutable, and
the user can look back at how the simulation evolved over its most recent ticks.

Users are not necessarily co-located with the machine running the simulation. The
simulation engine can run on a dedicated backend (e.g., a lab/cluster machine or a cloud VM
with more memory/CPU than a laptop), while the user interacts with it from a separate
desktop GUI, potentially from a different machine on the same network. This is a deliberate decoupling: the entity that computes the micro-grid is independent from the entity that observes/controls it.

Interaction happens in two distinct patterns always through the desktop GUI:
\begin{itemize}
    \item \textbf{Configuration phase} (low frequency, interactive): the user defines a scenario through the
    DSL/GUI — topology, components, weather, tick duration — before the simulation starts.
    This happens once per scenario, or occasionally during authoring/debugging of a scenario.
    \item \textbf{Monitoring/control phase} (continuous, real-time): once running, the system streams a new
    state snapshot at every tick; a user watching the GUI dashboard receives updates at the
    configured tick rate (potentially several times per second), observing the evolving graph,
    energy flows, and statistics, and can at any time issue start/pause/step commands. This is
    a long-lived, continuous interaction, not a one-shot request/response.
\end{itemize}

In this project, data is closer to "simulation state" than classic personal user data:
\begin{itemize}
    \item  \textbf{Scenario configuration} — authored/held client-side until a simulation is created on the backend.
    \item \textbf{Simulation state}, modeled as two parts: an immutable static model (topology, entity
    specifications) and dynamic state (environment, battery charge, flows), held by the backend actors.
    \item \textbf{Event history}: every state transition is persisted as an event (event sourcing) in a
    persistence journal, plus periodic snapshots, both kept in a Redis store shared by all
    backend nodes, enabling crash recovery (even on a different node). The journal is a
    recovery mechanism rather than an archive: entity events already covered by a snapshot are
    deleted, so what is retained is enough to rebuild the \emph{current} state of a run, not
    its whole past.
    \item \textbf{Telemetry stream}: per-tick snapshots are also published to Kafka topics so that GUI
    clients (and, potentially, external analytics consumers) can observe simulation evolution
    without querying the backend state directly. Within the broker's retention, these topics
    also hold the per-tick history of a run, which a GUI replays from the beginning when it
    opens a simulation.
\end{itemize}

\section{Distribution motivations}

Distribution in GridSim is motivated by a combination of factors; the dominant ones are
resource sharing/separation of concerns and fault tolerance, with computation parallelism
and geographic distribution as secondary but still relevant drivers.

\begin{itemize}
    \item \textbf{Resource sharing and separation of concerns}. The simulation engine and the GUI have very
    different resource profiles and lifecycles: the engine is CPU/state-heavy and must run
    continuously and deterministically tick after tick, while the GUI is interaction-heavy and
    must stay responsive regardless of how expensive a tick computation is. By decoupling them
    (HTTP for control, Kafka for streaming telemetry), several GUI instances can observe the
    same backend simulation concurrently, a single backend can host multiple concurrent
    simulations, and a user is never forced to run the heavy simulation process on their own desktop, it can be hosted on a shared, more capable machine.
    \item \textbf{Computation speedup / parallelism}. A micro-grid is naturally decomposable: each entity
    (house, panel, storage) evolves largely independently within a tick, subject to the
    topology constraints resolved afterwards by the power-flow solver. This maps directly onto
    Pekko's cluster sharding: entities are distributed across (potentially many) shard regions
    and evolved concurrently, rather than sequentially in a single-threaded loop. This allows
    larger micro-grids (more entities) to be simulated and allows horizontal scaling by adding more
    backend nodes to the cluster as the simulated grid grows.
    \item \textbf{Fault tolerance}. Because the simulation state is valuable and the system is meant to run continuously, the architecture uses event sourcing (every state transition persisted as an event) plus periodic snapshotting, together with actor supervision strategies and automatic recovery on restart. This means an Entity or Simulation crash does not lose any already persisted state transition and the system can resume from the
    last known consistent state rather than failing the whole simulation. Since the journal and snapshots live in a Redis store outside the backend nodes, this holds even when the node hosting a simulation crashes: the simulation is re-spawned on a surviving node and recovers the same state there.
    \item  \textbf{Geographic/organizational distribution}. the HTTP+Kafka boundary between GUI and backend is designed precisely so that a GUI client can be run anywhere with network access to the backend's exposed endpoints, which is relevant for scenarios such as a shared simulation server observed by multiple
    analysts from different workstations.
\end{itemize}

  \section{Glossary}
  \label{sec:glossary}

  \begin{description}
    \item[Micro-grid] A local electrical network modeled as a graph of
  energy
      entities connected by cables.
    \item[Tick] A discrete simulation time step, of user-configured
  duration,
      at which the system recomputes environment and entity states.
    \item[Entity] A node of the micro-grid graph: House, SolarPanel,
  Storage,
      or External Grid.
    \item[House] An entity combining a consumption profile with optional
  local
      production (SolarPanel) and storage (battery).
    \item[SolarPanel] A production entity whose output depends on
  irradiance,
      surface, and efficiency.
    \item[Storage / Battery] An accumulation entity bounded by maximum
      capacity, maximum charge/discharge power, and a minimum
  state-of-charge
      threshold.
    \item[Cable] An edge of the micro-grid graph, with a maximum
      power-transport capacity.
    \item[External Grid] A special node acting as an infinite energy
      source/sink, absorbing or providing any residual imbalance.
    \item[SoC (State of Charge)] The current stored energy level of a
  battery,
      relative to its capacity.
    \item[Power flow] The distribution of power across cables resulting from
      nodal energy balances.
    \item[DSL (Domain Specific Language)] The embedded Scala language used
  to
      declaratively describe a scenario.
    \item[SimulationActor] The actor orchestrating the tick cycle of one
      simulation instance.
    \item[EntityActor] A sharded actor owning the evolution of one grid
      entity.
    \item[Cluster sharding] The Pekko mechanism distributing actor instances
      (e.g., EntityActors) across cluster nodes.
    \item[Event sourcing] Persistence pattern storing state changes as an
      append-only sequence of events rather than mutable records.
    \item[Snapshot] A periodic, consolidated copy of an actor's state used
  to
      bound recovery time.
    \item[Telemetry] The stream of per-tick simulation/entity snapshots
      published to Kafka for external consumption.
  \end{description}

  \section{Relevant Distributed System Features}
  \label{sec:distributed-features}

  GridSim is split into a backend simulation engine and a GUI client precisely because specific
  distributed-system properties are needed. This section motivates, feature
  by feature, which properties matter for the project and which are explicitly
  out of scope.

  \begin{description}

  \item[Transparency --- relevant (location transparency), not relevant
    (hiding failures from the user).]
  Cluster sharding gives \emph{location transparency} for entities: a
  \texttt{SimulationActor} addresses an \texttt{EntityActor} by logical id
  (\texttt{simulationId-localId}) without knowing which physical node
  currently hosts it, and the shard can be rebalanced across nodes without
  changing calling code. This is actively used, since entity placement is
  meant to scale with grid size. Conversely, \emph{full} transparency toward
  the human user (hiding every failure or delay) is \textbf{not} a goal: the
  GUI is intended to surface a ``disconnected/degraded'' state when the
  backend or Kafka is unreachable,
  rather
  than hide it --- operators need to know when they are looking at stale
  data.

  \item[Fault tolerance / dependability --- highly relevant.]
  The simulation represents potentially long-running,
  non-trivial-to-recompute
  state, so uninterrupted service and no silent data loss are explicit
  goals:
  state changes are event-sourced, periodic snapshots bound recovery time,
  and
  both \texttt{SimulationActor} and \texttt{EntityActor} use a
  restart-with-backoff supervision strategy with automatic recovery
  (\texttt{RecoveryCompleted} re-arming the tick timer). Events and snapshots are written to a
  Redis store shared by all backend nodes, so the loss of a single node does not lose the
  simulations it was hosting: they are re-spawned elsewhere and recover from the same store.

  \item[Scalability --- relevant.]
  The system is designed to scale with the \emph{size of the simulated grid}
  (number of entities), not with number of end users: cluster sharding
  allows
  entity computation to be spread across nodes as a scenario grows, and
  multiple independent simulations can coexist (tracked by the
  \texttt{SimulationRegistryActor}). Scaling to many concurrent \emph{human
  users/tenants} is not a design goal --- GridSim remains an
  engineering/educational tool used by a small number of operators per
  deployment.

  \item[Resource sharing --- relevant.]
  Decoupling the engine from the GUI via HTTP (control) and Kafka
  (telemetry)
  exists precisely so that the simulation process
  can
  be hosted once and shared: several GUI clients can observe the same
  running
  simulation, and one backend can run several simulations concurrently. This
  is the second primary distribution driver, alongside fault tolerance.

  \item[Evolvability, maintainability --- relevant]
  The Functional Core/Imperative Shell and Observer-based dispatch patterns
  keep the simulation engine, statistics, and GUI independently evolvable.
  This requirement is satisfied largely through modular design rather than
  through distribution mechanisms per se, though the explicit HTTP/Kafka
  contracts also reduce coupling between backend and client releases.

  \item[Performance, concurrency, computation/communication efficiency ---
    relevant.]
  Per-tick computation is intentionally parallelized across
  \texttt{EntityActor}s rather than computed in a single sequential loop,
  which is a direct efficiency/concurrency motivation for using an
  actor-based, shardable runtime. Network usage (Kafka telemetry volume,
  HTTP
  control latency) matters insofar as it must not interfere with real-time
  GUI updates; efficiency is a secondary
  requirement rather than a hard constraint.

\end{description}

\section{Design}\label{design}


\subsection{Architecture}\label{architecture}

GridSim adopts a \textbf{client--server architectural style} in which the server itself is an
internally distributed, actor-based system: the backend (one or more Apache Pekko cluster
nodes) hosts the simulation engine behind a stable logical address space, while an arbitrary
number of GUI clients connect to it over the network. Three complementary patterns refine this
top-level style:

\begin{itemize}
  \item \textbf{Actor model with cluster sharding} for the backend itself. Each simulation
  and each grid entity is modeled as an independent, uniquely addressable, stateful actor
  (\texttt{SimulationActor}, \texttt{EntityActor}). This directly serves \textsc{FR-15} (multiple independent
  concurrent simulations) and \textsc{NFR-6} (horizontal scalability with the number of
  entities): entities evolve concurrently and are transparently distributed/rebalanced across
  cluster nodes by Pekko's cluster sharding, with no change to application logic as the
  cluster grows. This choice is a direct consequence of the \emph{computation
  parallelism} and \emph{scalability} distribution motivations discussed in
  \cref{sec:distributed-features}.
  \item \textbf{Separate control and data planes} between client and server: a synchronous
  HTTP REST API (Pekko HTTP) is used for low-frequency lifecycle commands and queries
  (\textsc{FR-12}, \textsc{FR-13}), while an asynchronous Kafka publish/subscribe channel
  carries the high-frequency, continuous telemetry stream (\textsc{FR-14}). Splitting these
  two very different interaction shapes into two different transports/protocols, instead of
  multiplexing both onto a single connection, keeps each plane simple and lets any number of
  GUI instances (or non-GUI consumers) subscribe to the data plane independently from who
  issues control commands --- directly serving the \emph{resource sharing} motivation.
  \item \textbf{Functional core, imperative shell} inside each simulation. The actual tick
  transition ($S_{t+1} = \mathit{step}(S_t)$: environment advance, per-entity evolution,
  power-flow resolution) is implemented as pure, side-effect-free functions over immutable
  data (\textsc{NFR-1}); the surrounding actor (\texttt{SimulationActor}) is the only
  component allowed to perform effects (scheduling, persistence, publishing). This keeps the
  domain logic deterministic and trivially unit-testable in isolation from the distributed
  runtime, while confining all actor-related complexity (timeouts, retries, recovery, see
  \cref{fault-tolerance}) to a thin imperative layer.
\end{itemize}

On the client side, the GUI is a passive, stateles observer
(\cref{behaviour}): it never holds authoritative simulation state, only a reactive projection
of what the backend publishes, which satisfies \textsc{NFR-2} (the UI thread is never blocked
by tick computation, since computation happens entirely on the backend and the UI only reacts
to asynchronous messages).

\subsection{Infrastructure}\label{infrastructure}

Five infrastructural component \emph{kinds} appear in the design:

\begin{itemize}
  \item \textbf{Backend node(s)}: one or more Apache Pekko \texttt{ActorSystem} processes
  (\texttt{GridSimAgentSystem}) forming a single cluster. Each node hosts shard regions for
  \texttt{EntityActor} and \texttt{SimulationActor}, so adding nodes increases the number of
  shard regions available to host entities (\textsc{NFR-6}).
  \item \textbf{HTTP API endpoint}: a Pekko HTTP server bound on every backend node
  (port \texttt{8080}) exposing \texttt{SimulationControlRoutes}, the control plane for
  \textsc{FR-12}/\textsc{FR-13}. In the containerized deployment the nodes are reached through
  an \textbf{HTTP gateway} that spreads requests across them and skips
  a node that stops answering, so clients only ever see one address (\cref{deployment}).
  \item \textbf{Message broker}: a single Apache Kafka broker acting as the data plane,
  carrying three logical topic families per simulation, satisfying \textsc{FR-14}.
  \item \textbf{Persistence store}: a single Redis instance shared by every backend node,
  holding the Pekko Persistence event journal and snapshot store of all actors. Keeping it
  outside the backend nodes is what lets an actor recover its state on whichever node it is
  re-spawned on (\cref{data-and-consistency-issues}).
  \item \textbf{GUI client(s)}: one or more ScalaFX desktop processes, each independently subscribing to the data plane and issuing control-plane
  calls.
\end{itemize}

\textbf{Network placement.} Backend nodes, the Kafka broker and the Redis store are expected
to sit on the same machine (or the same trusted network; the provided \texttt{compose.yml} runs
them as containers of one Compose project), while GUI clients may run on a \emph{different} host on
that same network. A \texttt{Launcher} entry point selects at startup whether a given process
runs as \texttt{backend} (\texttt{ActorMain}: a single-node backend with in-memory
persistence, for local development), as \texttt{backend-cluster} (\texttt{ClusterMain}: one
replica of the clustered backend, configured through environment variables and used in the
containerized deployment), or as \texttt{gui} (the ScalaFX client).

\textbf{Discovery/naming.} Two different, deliberately simple naming mechanisms are used,
reflecting the project's small-scale deployment scope:
\begin{itemize}
  \item \emph{Inside} the backend cluster, nodes find each other through seed nodes. In the
  containerized deployment no address is configured by hand: each replica resolves the name of
  its Compose service (\texttt{CLUSTER\_SERVICE\_NAME}) through Docker's internal DNS and uses
  every address returned as a seed node, so replicas can be added or restarted without
  reconfiguring the others; an explicit list (\texttt{PEKKO\_SEED\_NODES}) can be given
  instead, and the single-node \texttt{ActorMain} simply uses itself. Once joined, \emph{entities} are
  addressed by stable logical identifiers (\texttt{simulationId} for a
  \texttt{SimulationActor}, \texttt{simulationId-localId} for an \texttt{EntityActor}) that
  cluster sharding resolves to a physical node transparently, giving \emph{location
  transparency} as already motivated in \cref{sec:distributed-features}.
  \item \emph{Between} client and server, there is no discovery layer at all: the GUI is
  pointed directly at the HTTP gateway and the Kafka broker via CLI arguments
  (\texttt{--api}, \texttt{--kafka}, defaulting to \texttt{localhost}).
\end{itemize}

\subsection{Modelling}\label{modelling}

\textbf{Domain entities.} The micro-grid is modeled as a graph of \texttt{GridEntity}
implementations --- \texttt{House}, \texttt{SolarPanel}, \texttt{Storage} (battery), and a
singleton \texttt{ExternalGrid} --- connected by \texttt{Cable} edges into a \texttt{GridGraph}
(\cref{sec:glossary}), plus a global \texttt{Environment} capturing simulated time, irradiance
and temperature. Every entity type keeps its \emph{static} configuration (capacity, surface,
efficiency, \ldots) and its \emph{dynamic} state (e.g.\ \texttt{HouseState},
\texttt{StorageState}) as separate, immutable case classes, both implementing the shared
\texttt{GridEntity}/\texttt{GridEntityState} abstractions so the engine can treat every entity
uniformly.

\textbf{Mapping to infrastructure.} State is deliberately asymmetric, server-authoritative:
the \emph{static} model (\texttt{SimulationModel}: topology and entity specifications) and the
per-entity \emph{dynamic} state are both owned by the backend, one \texttt{EntityActor} per
grid entity and one \texttt{SimulationActor} per simulation. The GUI client never owns authoritative state: it only
holds a short-lived, reactive \emph{projection} of whatever was last received from Kafka,
rebuilt from scratch whenever a client (re)connects. The durable copy --- the events and
snapshots needed to rebuild the current state --- lives exclusively in each actor's own persistence journal, held in the shared Redis
store rather than on the node hosting the actor, and is \emph{not}
duplicated in Kafka: Kafka carries transient, fire-and-forget notifications that are not
required for correctness (see \cref{data-and-consistency-issues}), while the Kafka log itself
retains every published tick within its retention period, which is what a newly connected
client replays to catch up on a run's past ticks.

\textbf{Domain events.} Three per-aggregate event streams are persisted for recovery/event
sourcing: \texttt{SimulationEvent} (\texttt{Initialized}, \texttt{Started}, \texttt{Paused},
\texttt{Stopped}, \texttt{TickAdvanced}, \texttt{SpeedUpdated}, \texttt{TickDeltaUpdated}) for
\texttt{SimulationActor}, \texttt{EntityEvent} (\texttt{Initialized}, \texttt{Evolved}) for
\texttt{EntityActor}, and \texttt{SimulationRegistryActor.Event}
(\texttt{SimulationRegistered}, \texttt{SimulationUnregistered}) for the cluster-wide registry
of existing simulations. Separately, three kinds of \emph{outward notifications} are broadcast on
Kafka at run time: a per-entity telemetry snapshot, a per-tick global snapshot (environment and
cable loads), and a control/status update (including the \texttt{degraded} flag, see
\cref{fault-tolerance}) --- these are observations of state changes, not themselves part of the
persisted domain log.

\textbf{Messages.} Three categories are exchanged, matching the classic command/event/query
split: \emph{commands} sent as actor messages from the HTTP layer or from an internal scheduler
to a specific actor (\texttt{Initialize}, \texttt{Start}, \texttt{Pause}, \texttt{Step},
\texttt{Stop}, \texttt{UpdateSpeed}, \texttt{UpdateTickDelta}, and the internal
\texttt{Evolve}/\texttt{TickTimer}); \emph{queries}, answered synchronously via the
request--reply (\emph{ask}) pattern (\texttt{GetStatus}, the simulation list); and
\emph{events/notifications}, which flow one way, either persisted (the domain events above) or
broadcast on Kafka (telemetry).

\textbf{System state.} At any point in time the state of one simulation comprehends: the
static \texttt{SimulationModel} (graph, entity specs); the dynamic \texttt{SimulationState}
(current \texttt{Environment}, each entity's \texttt{GridEntityState}, net energy
\texttt{Flow} per entity, and resolved load per \texttt{Cable}); the \texttt{SimulationActor}'s
own lifecycle metadata (\texttt{Status}, current tick number, run-time configuration such as
speed/tick delta, and transient failure-handling counters, \cref{behaviour}); and, at the
cluster level, a registry of which simulation ids/presets currently exist
(\texttt{SimulationRegistryActor}, itself event-sourced and running as a cluster singleton), used
to answer the ``list simulations'' query.

\subsection{Interaction}\label{interaction}

Interaction happens along two independent planes, deliberately kept separate (\cref{architecture}):

\begin{itemize}
  \item \textbf{Control plane (HTTP, request/reply and fire-and-forget).} A GUI, or any other
  HTTP client (\textsc{FR-13}), calls \texttt{SimulationControlRoutes} to create a simulation
  or issue lifecycle commands. Fire-and-forget \emph{tell} is used for commands with no
  meaningful return value (\texttt{start}, \texttt{pause}, \texttt{step}, \texttt{delete}),
  while the \emph{ask} pattern (request/reply with a timeout) is used for queries that need an
  answer (\texttt{status}, the simulation list). Every call is routed, through cluster
  sharding's \texttt{EntityRef}, to the single \texttt{SimulationActor} instance owning that
  simulation id, wherever in the cluster it currently lives.
  \item \textbf{Data plane (Kafka, publish/subscribe).} The backend is the sole producer on
  three per-simulation topics (entities, ticks, control); any number of GUI instances (or
  external analytics consumers, \cref{sec:distributed-features}) subscribe independently,
  decoupled in both time and multiplicity from the producer and from each other
  (\textsc{FR-14}).
  \item \textbf{Internal scatter/gather (actor ask, bounded by timeout).} Once running, on
  every tick the \texttt{SimulationActor} \emph{scatters} an \texttt{Evolve} ask-request to
  every \texttt{EntityActor} of the simulation, in parallel, and \emph{gathers} all replies
  via \texttt{Future.sequence} piped back to itself as a single message
  (\texttt{EntitiesEvolved} on success, \texttt{TickFailed} on timeout/exception). This keeps
  the \texttt{SimulationActor}'s own single-threaded mailbox non-blocking while entity
  evolutions genuinely execute concurrently (\textsc{NFR-6}).
\end{itemize}

\subsection{Behaviour}\label{behaviour}

\texttt{SimulationActor} --- stateful, explicit finite-state machine. Its
\texttt{Status} is one of \texttt{Idle} (just initialized, awaiting \texttt{Start}),
\texttt{Running} (actively scheduling ticks), \texttt{Paused} (suspended, resumable), or
\texttt{Stopped} (terminal: no command restarts it). \texttt{Start} moves
\texttt{Idle}/\texttt{Paused} $\rightarrow$ \texttt{Running} and self-schedules the first
\texttt{TickTimer}; while \texttt{Running}, each \texttt{TickTimer}/\texttt{EntitiesEvolved}
pair advances the tick counter and schedules the next timer; \texttt{Pause} moves
\texttt{Running} $\rightarrow$ \texttt{Paused}; \texttt{Stop} moves any non-terminal state to
\texttt{Stopped} unconditionally. Besides the persisted lifecycle, the actor keeps small,
\emph{transient} (non-persisted) bookkeeping --- \texttt{consecutiveFailures} and a
\texttt{degraded} flag --- purely to drive the retry/backoff behaviour of
\cref{fault-tolerance}.

\textbf{\texttt{EntityActor} --- stateful, simpler reactive behaviour.} It reacts only to
\texttt{Initialize} (adopt static config and initial dynamic state) and \texttt{Evolve}
(compute and persist the next dynamic state and net energy flow for one tick, replying with
the result); it has no explicit multi-state machine, only the presence/absence of its
configuration and the bookkeeping (\texttt{lastTick}, \texttt{lastFlow}) needed for
idempotent retries.

\textbf{\texttt{SimulationRegistryActor} --- minimal, event-sourced bookkeeping.} It keeps a
map from simulation id to preset name, updated on \texttt{RegisterSimulation}/
\texttt{UnregisterSimulation} and read on \texttt{GetSimulations}. In cluster mode it runs as a
\emph{cluster singleton} (one instance for the whole cluster, hosted on the oldest node) and is
event-sourced: each registration/unregistration is first persisted as a
\texttt{SimulationRegistered}/\texttt{SimulationUnregistered} event and only then acknowledged,
so when the singleton migrates to another node after a crash it rebuilds the same list by
replaying its events from the shared store (\cref{availability}). It uses the same
\texttt{restartWithBackoff} strategy on persistence failures as the other two actors.

\textbf{GUI --- effectively stateless from the server's point of view.} Views are purely
declarative bindings; ViewModels are the only locally stateful components, caching the latest
value received per channel as JavaFX reactive properties; a \texttt{Coordinator} mediates the
Kafka subscriptions so views/view-models never deal with asynchronous I/O directly (MVVM, see
also the project's own detailed-design notes).

\textbf{State ownership and update timing.} All \emph{authoritative} state transitions
happen exclusively inside the backend's actors: \texttt{SimulationActor} persists a lifecycle
event whenever a command succeeds and a \texttt{TickAdvanced} event once all entities have
replied for a tick; \texttt{EntityActor} persists an \texttt{Evolved} event every time it
actually computes (as opposed to replays) a tick. The GUI never updates system state --- it
only updates its own \emph{presentation} state, once per Kafka message received, which means
the view is eventually consistent with, and always slightly behind, the authoritative backend
state.


\subsection{Data and Consistency Issues}\label{data-and-consistency-issues}

\textbf{Persisted data.} Three things are persisted: (a) the events of every
\texttt{SimulationActor} and \texttt{EntityActor} (lifecycle and per-tick evolution events), so
that a crash never loses an already confirmed state transition; (b) periodic snapshots of
\texttt{EntityActor} state (every 100 events, retaining the last 2) to bound recovery time
after many ticks; and (c) the events of the \texttt{SimulationRegistryActor}, so that the list
of existing simulations survives the loss of the node hosting it. The retention policies differ
between the two simulation actors. \texttt{SimulationActor} keeps all of its events, which are
small (lifecycle changes, and one \texttt{TickAdvanced} per tick carrying the environment and the
tick number). \texttt{EntityActor} deletes the events already covered by its retained
snapshots, so for each entity only the latest snapshots and the few hundred events after them
are kept. The journal is therefore sufficient to rebuild the \emph{current} state of every
simulation after a crash, but not the state of the grid at an arbitrary past tick.

The per-tick history of a run is instead available, as a side effect, in the Kafka telemetry
topics,
which carry every entity state, net flow and cable load published at each tick. When a GUI
opens a simulation it re-reads these topics from the beginning and
replays every past tick through the statistics engine; this is how the statistics panel shows
the run's evolution so far (the net-flow chart keeps the latest 200 ticks) rather than only
the ticks received after the window was opened (\textsc{FR-9}). It is
an observation log for clients, not part of the recovery path: losing it never affects the
backend's state.

\textbf{Storage mechanism.} Pekko Persistence's event-sourcing abstraction is used
: each aggregate (one \texttt{SimulationActor} or
\texttt{EntityActor} per id) already is a single, independently addressable unit with its own
append-only event log keyed by \texttt{PersistenceId}, which maps onto a
key-value-shaped.
There is no cross-aggregate join ever needed, since each actor only ever reads/replays its
\emph{own} history.

In cluster mode (\texttt{ClusterMain}) both the journal and the snapshot store are custom Pekko
Persistence plugins backed by a single \textbf{Redis} instance shared by every node
(\texttt{RedisJournal} and \texttt{RedisSnapshotStore}). The
store sits outside every backend node, so an actor re-spawned on a different node after a crash
reads exactly the events and snapshots its previous incarnation wrote. The key-value shape of
the data maps directly onto Redis structures

\textbf{Store access patterns and concurrency.} Only the owning actor instance ever
reads its own persisted events/snapshots, and only once, during recovery after a (re)start
(\texttt{RecoveryCompleted}); no other component queries the persistence store directly. Writes
are append-only and issued exclusively by that same actor instance. Cluster sharding guarantees
at most one live instance of a given \texttt{persistenceId} across the whole cluster at any
time (the \emph{single-writer} invariant), so concurrent writes to the same aggregate's journal
are structurally impossible by construction, and there is consequently no need for
optimistic/pessimistic locking or conflict resolution on the write path. Every node \emph{could} technically write to any key in
Redis, and it is sharding that guarantees only one of them ever writes a given \texttt{persistenceId}.

\textbf{Data shared between components.} The per-tick \texttt{SimulationState} (environment,
every entity's dynamic state, net flows, cable loads) is conceptually shared across
\texttt{SimulationActor} and all of a simulation's \texttt{EntityActor}s, but never through
shared mutable memory: each \texttt{EntityActor} owns and mutates only its own slice (its
\texttt{GridEntityState}), returns it as an immutable value, and \texttt{SimulationActor}
\emph{composes} the returned flows afterwards (feeding them to the power-flow solver) rather
than reaching into another actor's state --- sharing by message-passing and composition, not by
reference, which is what makes the single-writer property above hold.

\subsection{Fault-Tolerance}\label{fault-tolerance}

\textbf{Replication.} Redundancy is provided at two complementary levels. \emph{Placement}
redundancy comes directly from cluster sharding: if a node leaves the cluster, every actor it
was hosting is automatically re-spawned on a surviving node, with no operator intervention,
and recovers by replaying its own persisted event log. \emph{State} durability is delegated
entirely to the configured Pekko Persistence journal/snapshot-store plugin
(\cref{data-and-consistency-issues}) rather than to ad-hoc application code, and the
2-snapshot retention kept for each \texttt{EntityActor} is what keeps that replay fast.

The two levels only work together because the store is shared: the surviving node reads the
crashed node's events from Redis rather than from a journal that disappeared with it. In
concrete terms, recovery from a node crash proceeds as follows:
\begin{itemize}
  \item the \texttt{SimulationActor} shard region is started with \emph{remember entities}
  enabled, so the simulations that were active on the lost node are re-spawned on a surviving
  node straight away, without waiting for a new HTTP request to reach them; each replays its
  events and, on \texttt{RecoveryCompleted}, re-arms its tick timer if it was
  \texttt{Running};
  \item each \texttt{EntityActor} is re-spawned lazily by sharding on the next \texttt{Evolve}
  sent to it, and recovers from its latest snapshot in Redis plus the events written after it;
  \item the \texttt{SimulationRegistryActor} singleton is restarted on the new oldest node and
  replays its registration events, so the list of simulations seen by the GUI is unchanged.
\end{itemize}
Redis itself is the one component of this chain that is not replicated: it runs as a single
instance with no replica or Sentinel and, in the provided \texttt{compose.yml}, without a
mounted volume. It removes the backend nodes as points of failure for state, but is itself one.

\textbf{Heart-beating / timeout / retry.} Three mechanisms operate at different scopes:
\begin{itemize}
  \item \emph{Cluster-level heart-beating}: Pekko's cluster membership protocol continuously
  monitors node liveness and feeds a \textbf{Split Brain Resolver} configured with the
  \texttt{keep-majority} strategy and a 10-second stabilization window --- after a network
  partition, only the majority side is kept alive, which is what makes the single-writer
  invariant of \cref{data-and-consistency-issues} hold even under partial network failures.
  \item \emph{Per-tick timeout}: every \texttt{Evolve} ask-request from
  \texttt{SimulationActor} to an \texttt{EntityActor} carries a configurable
  \texttt{tickTimeout}; if any single entity fails to answer in time, the whole tick's
  \texttt{Future.sequence} fails and the actor treats it as \texttt{TickFailed}.
  \item \emph{Retry with exponential backoff}: on \texttt{TickFailed}, \texttt{SimulationActor}
  does not retry immediately but reschedules the next \texttt{TickTimer} after
  $\min(\mathit{base} \times 2^{\mathit{failures}-1}, \mathit{max})$ (defaults: 1\,s base,
  30\,s cap), to avoid hammering an already-struggling dependency. After a configurable number
  of consecutive failures (default 3) the simulation marks itself \texttt{degraded} and
  broadcasts this on the control topic, so every connected GUI can visibly surface the
  degradation instead of silently showing stale data.
\end{itemize}

\textbf{Idempotent retries (avoiding double processing).} Because a retried tick re-sends
\texttt{Evolve} for the \emph{same} tick number, \texttt{EntityActor} remembers the last tick
it actually completed (\texttt{lastTick}); if asked again for a tick it has already processed,
it replies with its cached result instead of recomputing (and, crucially, without persisting a
second \texttt{Evolved} event) --- preventing duplicate energy accounting and duplicate
persisted events under Pekko's at-least-once delivery semantics.

\textbf{Error handling / supervision.} All three event-sourced actors (\texttt{SimulationActor},
\texttt{EntityActor} and \texttt{SimulationRegistryActor}) declare an explicit
\texttt{onPersistFailure} supervision strategy
(\texttt{restartWithBackoff}, 200\,ms--5\,s, 0.2 jitter): on a crash or persistence failure,
the faulty instance is torn down and a fresh one is restarted (transparently re-homed by
cluster sharding if needed), which replays its persisted events/snapshot and, via the
\texttt{RecoveryCompleted} signal, automatically re-arms the tick timer if the simulation was
\texttt{Running} when it crashed --- so, from an operator's perspective, a crash shows up as a
brief pause rather than data loss. Kafka publishing failures are treated as strictly
\emph{non-critical}: publishers sit behind a small interface with a \texttt{NoOp}
implementation, and a failure to publish telemetry never blocks or fails a tick --- simulation
correctness never depends on telemetry delivery succeeding, only on the event-sourced journal.

\subsection{Availability}\label{availability}

\textbf{Caching.} The only cache-like mechanisms are local to a single actor/process and
exist for a specific, narrow reason rather than as a general performance optimization:
\texttt{EntityActor}'s \texttt{lastFlow}/\texttt{lastTick} let a retried request be answered
without recomputation (\cref{fault-tolerance}), and GUI ViewModels keep the latest received
snapshot per channel so the interface always has something to render between two Kafka
messages. No shared/distributed cache is used: per-tick state is already cheap
to keep in the owning actor's memory, and introducing a second copy of that state elsewhere
would only reopen the consistency problem that single ownership is designed to avoid.

\textbf{Behaviour under network partitioning.} The Split Brain Resolver
(\cref{fault-tolerance}) governs this case: on a partition, the minority side is
unconditionally downed (its shard regions and hosted actors stop), so it cannot keep accepting
writes and silently diverge from the majority side, preserving the single-writer invariant
relied upon by event sourcing. A GUI client connected to the minority side simply loses its
HTTP/Kafka connection and surfaces that as a disconnection, rather than being fooled into
showing locally-computed, inconsistent data. The \texttt{SimulationRegistryActor} follows the
same logic: as a cluster singleton it lives on exactly one node of the surviving majority, and
because it is event-sourced into the shared store, moving it to another node (after a crash or
after the minority is downed) loses no registered simulation. Once the partition is resolved,
the actors re-spawned on the majority side read from Redis exactly the state that was last
persisted before the split.

\section{Implementation}\label{implementation}

\textbf{Network protocols.} Three protocols connect the system's components, each matching the
traffic shape of the channel it serves. The GUI drives simulation lifecycle commands
(create/start/pause/step/stop, speed and tick-delta updates) through a synchronous
\textbf{HTTP} API exposed by Pekko HTTP (\texttt{SimulationControlRoutes}) and consumed via
Java's built-in \texttt{java.net.http.HttpClient} (\texttt{HttpSimulationApiClient}) ---
request/response is a natural fit for these infrequent, one-shot commands. High-frequency
telemetry (per-tick entity state, grid-wide tick summaries, control-channel broadcasts) instead
flows one-way from backend to every connected GUI over \textbf{Apache Kafka}'s wire protocol, a
publish/subscribe shape that cleanly supports multiple simultaneous GUI consumers without the
backend tracking who is listening. Internally, the nodes forming the
Pekko cluster communicate over \textbf{Pekko Artery} (TCP transport), which cluster sharding and
the Split Brain Resolver rely on to exchange membership and
entity-location information.

\textbf{In-transit data representation.} Representation follows the same three-way split.
HTTP request/response bodies are \textbf{JSON}, marshalled with Pekko HTTP's \texttt{spray-json}
integration on both the server (\texttt{SimulationControlRoutes}) and client
(\texttt{HttpSimulationApiClient}) sides. Kafka payloads are \textbf{Protocol Buffers} messages,
generated by ScalaPB from the schemas in the dedicated \texttt{protocols} Gradle module
(\texttt{common.proto}, \texttt{entity\_state.proto}, \texttt{simulation\_data.proto}) and
encoded/decoded through \texttt{SimulationDataCodecs} --- chosen over JSON for its compact
binary footprint, given the volume of per-tick, per-entity messages; the one exception is the
lightweight control-channel broadcast (status/speed/tick-delta/degraded), which uses a minimal
hand-rolled pipe-delimited UTF-8 string (\texttt{SimulationControlCodec}), since a handful of
primitive fields did not justify a full schema. Pekko's own remote messages (actor protocol case
classes crossing node boundaries inside the cluster) use plain \textbf{Java serialization}: the
project's \texttt{Serializable} marker trait, extended by every actor command, event, reply and
state, and by the domain model classes they carry, extends \texttt{java.io.Serializable}, and
\texttt{ClusterMain} explicitly enables Pekko's Java serializer
(\texttt{allow-java-serialization = on}). The same serializer therefore also encodes the events
and snapshots stored in Redis (\cref{data-and-consistency-issues}). It required no per-message
schema or mapping, at the cost of a less compact format and of tying the stored data to the
exact class definitions; the \texttt{pekko-serialization-jackson} module is on the classpath but
is not bound to any message type.

\section{Validation}\label{validation}

\subsection{Automatic Testing}\label{automatic-testing}

\textbf{Unit testing.} 51 ScalaTest specs (\texttt{AnyFlatSpec} with \texttt{Matchers}, run
through \texttt{JUnitRunner}) under \texttt{app/src/test/scala} cover the logic that does not
need a running actor system: domain value objects (\texttt{Energy}, \texttt{Power},
\texttt{Flow}, \texttt{Irradiance}, \ldots), the two power-flow solvers
(\texttt{KirchhoffPowerFlowSolverSpec} and 
\texttt{SimplePowerFlowSolverSpec}), entity evolution strategies
(\texttt{SolarPanelStrategySpec}, \texttt{BatteryStrategySpec}, \texttt{HouseLogicSpec}), the
DSL builders and their validators (\texttt{HouseBuilderSpec},
\texttt{SimulationValidatorSpec}, \ldots), the Protobuf codecs
(\texttt{SimulationDataCodecsSpec}, round-tripping every message type), and the statistics
engine, whose module was developed test-first (TDD).

\textbf{Actor and HTTP-route testing.} \texttt{EntityActorSpec} and \texttt{SimulationActorSpec}
exercise the two event-sourced behaviours directly through Pekko's
\texttt{ActorTestKit} and \texttt{PersistenceTestKit}: initialization, state carried forward across
ticks, event persistence and replay after a restart, and snapshot persistence once the
retention threshold (100 events) is reached. The persistent registry is checked in
\texttt{SimulationRegistryActorTest}: stopped and re-spawned with the same
\texttt{PersistenceId}, it recovers the simulations registered before the stop. Finally,
\texttt{SimulationControlRoutesTest} drives the
HTTP layer (\texttt{SimulationControlRoutes}) through \texttt{pekko-http-testkit} without a real
socket, checking the simulation-listing and preset-validation paths.

\textbf{Fault-injection / corner-case testing.} The same two actor specs are also where the
mechanisms of \cref{fault-tolerance} are verified end-to-end: a tick that never gets all its
entity replies produces \texttt{TickFailed} without advancing the counter or publishing
telemetry; a batch that only partially completes leaves the already-persisted entities ahead of
the orchestrator, and a retry of that stalled batch does not re-evolve (hence does not
double-persist) those entities --- the idempotent-retry property is checked both at this
orchestrator level and directly on \texttt{EntityActor} for a retried and for a stale
\texttt{Evolve}; repeated \texttt{TickFailed} is checked to publish a \texttt{Degraded} control
update after the configured threshold and clear it on the next successful tick; and a
persistence failure on either actor is checked to restart it with backoff and resume correctly
(re-arming the tick timer for \texttt{SimulationActor}, replaying events for
\texttt{EntityActor}) rather than losing state.

\textbf{Integration testing.} Four specs under \texttt{app/src/test/integration} run against a
real Apache Kafka broker and are kept in a separate Gradle task, \texttt{integrationTest}, so
that the default \texttt{test} task (used in CI) never depends on Docker:
\texttt{integrationTest} itself depends on a \texttt{startKafkaContainer} task that launches an
\texttt{apache/kafka:latest} container (reusing one already listening on 9092, if present) and
is finalized by a matching \texttt{stopKafkaContainer} task. \texttt{KafkaTelemetryIntegrationSpec}
publishes real entity, tick, and multi-entity/multi-tick telemetry from
\texttt{EntityActor}/\texttt{SimulationActor} and consumes it back with a plain
\texttt{KafkaConsumer}, checking that the decoded Protobuf matches the original domain state
exactly. \texttt{RemoteSimulationBuilderIntegrationSpec} goes one step further, consuming that
same Kafka telemetry from the GUI side and checking that \texttt{RemoteSimulationBuilder}
updates its reactive snapshot/statistics signals accordingly.
\texttt{HttpApiUnavailableIntegrationSpec} and \texttt{KafkaUnavailableIntegrationSpec} are the
project's crash tests for its two external dependencies: pointing the HTTP client at an
unreachable host confirms it fails with a connect-timeout around its configured 5\,s timeout
rather than hanging, and that \texttt{RemoteSimulationBuilder.build} falls back to
\texttt{PAUSED} instead of blocking or throwing.

\textbf{Automation.} Both Gradle tasks are wired into the project's GitHub Actions workflow
(\texttt{.github/workflows/build.yml}), triggered on every push to \texttt{main}/\texttt{develop}
and on every pull request: an \texttt{assemble} job compiles the project
(\texttt{ciAssemble}) on Ubuntu with JDK 21, followed by a \texttt{build} job that runs
\texttt{ciBuild} (compile \texttt{+} unit \texttt{test}) across an Ubuntu/macOS/Windows matrix.
\texttt{integrationTest} is intentionally left out of this CI pipeline, since it depends on a
locally running Docker daemon, and is instead a developer-invoked task
(\texttt{./gradlew integrationTest}).

\textbf{Manual testing of the GUI.} The ScalaFX client is the one component validated manually

\section{Deployment}\label{deployment}

GridSim is deployed as two independent parts, matching the client--server split of
\cref{architecture}: the \emph{backend}, a Pekko cluster together with the Kafka broker and
the Redis store it depends on, shipped as a Docker Compose project; and the \emph{GUI}, a
desktop JVM application run directly on each operator's machine. A third, single-process mode
(\texttt{ActorMain}) exists only for local development and is not meant for deployment.

\textbf{Required software.}
\begin{itemize}
  \item \emph{Backend host}: Docker Engine with the Compose v2 plugin (\texttt{docker compose}).
  Nothing else is needed: the backend image is built from source inside Docker, and Kafka,
  Redis and Caddy are pulled as images (\texttt{apache/kafka:latest}, \texttt{redis:7-alpine},
  \texttt{caddy:2-alpine}).
  \item \emph{GUI host}: a \textbf{Java 21} JDK. The Gradle wrapper (\texttt{gradlew}) downloads
  the right Gradle version on first use, and JavaFX is fetched as a regular dependency for the
  current platform, so neither has to be installed separately.
\end{itemize}

\textbf{Installing and starting the backend from scratch.} From the root of the repository:
\begin{verbatim}
git clone <repository-url> GridSim-Distribuited
cd GridSim-Distribuited
docker compose up --build -d
\end{verbatim}
The first run builds the backend image, which takes a few minutes; later runs reuse it. The
expected outcome is:
\begin{itemize}
  \item \texttt{docker compose ps} lists \texttt{gridsim-kafka} and \texttt{gridsim-redis} as
  \emph{healthy}, three \texttt{backend} replicas and the \texttt{gridsim-gateway} container
  as running;
  \item \texttt{docker compose logs backend} shows, once per replica, the line
  \texttt{Cluster Simulation API Server online at http://<ip>:8080/}, after the replicas have
  joined a single cluster;
  \item \texttt{curl http://localhost:8080/api/simulations} answers with a JSON object
  containing an empty list of simulations.
\end{itemize}
The backend is stopped with \texttt{docker compose down}. Since no volume is mounted for Kafka
or Redis, this also discards the persisted state and the telemetry history
(\cref{data-and-consistency-issues}); \texttt{docker compose stop} keeps them.

\textbf{Starting the GUI.} On the operator's machine, from the same repository:
\begin{verbatim}
./gradlew :app:run --args="gui \
  --api=http://<backend-host>:8080 --kafka=<backend-host>:9092"
\end{verbatim}
Both arguments default to \texttt{localhost}, so they can be omitted when the GUI runs on the
backend host; \cref{user-guide} describes how the GUI is used once started. Alternatively,
\texttt{./gradlew :app:shadowJar} builds a self-contained jar
(\texttt{app/build/libs/GridSim.jar}) that is started with \texttt{java -jar GridSim.jar gui
\ldots}; \texttt{buildAmd64Jar}/\texttt{buildAarch64Jar} build the same jar for the other
processor architecture, bundling the matching JavaFX native libraries.

\textbf{Compose file.} \texttt{compose.yml} defines four services:
\begin{itemize}
  \item \texttt{kafka}: a single-node Kafka broker in KRaft mode (no ZooKeeper), with two
  listeners: \texttt{kafka:29092} for the backend containers on the Compose network and
  \texttt{localhost:9092}, published on the host, for GUI clients. A health check lists the
  topics to tell when the broker is ready.
  \item \texttt{redis}: the shared persistence store of \cref{data-and-consistency-issues},
  published on port \texttt{6379} and checked with \texttt{redis-cli ping}.
  \item \texttt{backend}: the image above, run as \texttt{replicas: 3} and started only once
  both \texttt{kafka} and \texttt{redis} report healthy (\texttt{depends\_on} with
  \texttt{condition: service\_healthy}), so no replica starts without its dependencies. The
  replicas publish no port on the host, which is what allows several of them to run side by
  side.
  \item \texttt{gateway}: a Caddy reverse proxy, the single entry point of the HTTP API on host
  port \texttt{8080}. It forwards each request to one of the backend replicas in round robin
  and stops sending traffic for 5\,s to a replica that failed twice, so the API stays
  reachable while a replica is down. Any replica can serve any request, because cluster
  sharding and the cluster singleton route it to the node that owns the target actor
  (\cref{infrastructure}).
\end{itemize}

\section{User Guide}\label{user-guide}

\textbf{Starting the system.} The backend must be started before the GUI, since the GUI only
ever talks to an already-running backend over HTTP/Kafka (\cref{implementation}) and has no
local simulation logic of its own. The backend is normally the clustered one, started with
\texttt{docker compose up -d} as described in \cref{deployment}; for quick local development,
\texttt{./gradlew :app:runBackend} instead launches the single-node \texttt{ActorMain}, which
binds the HTTP API on \texttt{0.0.0.0:8080} and connects to a Kafka broker on
\texttt{localhost:9092} (e.g.\ \texttt{docker compose up -d kafka}). In both cases
\texttt{./gradlew :app:runGui} launches \texttt{GuiApp}, the JavaFX client, which by default
points at \texttt{http://localhost:8080} and \texttt{localhost:9092}, i.e.\ at the gateway and
broker of a backend on the same machine. Both endpoints are overridable from the command line
(e.g.\ \texttt{./gradlew :app:runGui --args="--api=http://HOST:8080 --kafka=HOST:9092"}) to
point the GUI at a backend running on a different machine, which is what makes the
client--server split of \cref{architecture} usable across a real network; with the provided
\texttt{compose.yml} this also requires Kafka to advertise an address reachable from that
machine (\cref{deployment}).

\subsection{System Evaluation}

\textbf{Strengths of the product.} The actor model is used consistently rather than only
nominally: every \texttt{EntityActor} and \texttt{SimulationActor} owns its state exclusively and
is only ever touched through messages, so even though every tick evolves many entities
conceptually "in parallel", there is no shared mutable state and therefore no lock and no data
race to get wrong, by construction rather than by discipline. On top of that, cluster sharding
gives the system location transparency: \texttt{SimulationActor} addresses an \texttt{EntityActor}
by a stable id and never needs to know, or change, which physical node currently hosts it, which
is precisely what would let the set of simulations and entities scale across more machines without
touching the actors' own logic. Fault tolerance is handled the way a distributed system is
expected to: event sourcing into a store shared by all nodes
(\cref{data-and-consistency-issues}) makes every actor's state recoverable after
a restart, and also on a different node after the one hosting it has crashed; a repeatedly-failing tick is retried rather than
treated as fatal, and that retry is idempotent --- entities already evolved for a tick are
recognised and not re-evolved on a duplicate or retried message, which is exactly the
at-least-once delivery semantics a distributed system has to assume rather than the
exactly-once semantics it would be convenient (but wrong) to assume; and the Split Brain
Resolver's \texttt{keep-majority} strategy gives the cluster a principled, deterministic answer to
a network partition instead of leaving split-brain behaviour undefined. Finally, the backend and
every GUI client are decoupled through Kafka's publish/subscribe telemetry channel
(\cref{implementation}): several GUI instances can watch the same simulation concurrently without
the backend tracking who is listening, and because publishing is fire-and-forget from the
backend's side, a slow or disconnected GUI consumer cannot slow down or block the tick loop that
produces that telemetry. All of this is not only designed but verified: the crash tests in
\cref{automatic-testing} exercise the retry, idempotency, degraded-status and backoff-restart
behaviour against an actually failing dependency, not only against a diagram.

\textbf{Weaknesses of the product.} The most significant one is that moving persistence into
Redis has moved the single point of failure rather than removed it: the event journal and
snapshot store no longer depend on any backend node, but they all depend on one Redis instance
(\cref{fault-tolerance}), with no replica and, in the provided deployment, no persistent volume,
so losing that instance still loses every simulation regardless of how many backend nodes are in
the cluster. The journal plugin is also deliberately minimal: a batch of events is written with a
pipelined sequence of commands rather than inside a Redis transaction, and both events and
snapshots are stored with plain Java serialization (\cref{implementation}), which ties the
stored data to the exact class versions that wrote it. The same
single-point-of-failure pattern repeats on the Kafka side: every producer and
consumer in the project is configured against one broker address, so the pub/sub channel that
decouples backend and GUI concurrency is itself not fault-tolerant. Finally, none of the HTTP
control API or the Kafka topics require any credentials, which is a concurrency-adjacent weakness
too: in the current design, any client that can reach the cluster can issue commands or read
telemetry for every simulation, with no isolation between concurrently running simulations beyond
their ids.

\section{Future works}\label{future-works}

\textbf{Authentication and authorization.} Neither the HTTP control API nor the Kafka topics
require any credentials (\cref{implementation}), which is acceptable on the trusted local network
the project was developed and demonstrated on, but would need to change before exposing the system
beyond it. On the HTTP side this would mean adding a Pekko HTTP \texttt{SecurityDirective} (e.g.\
JWT bearer-token validation) in front of \texttt{SimulationControlRoutes}; on the Kafka side, it
would mean enabling SASL/TLS on the broker and configuring matching credentials in both
\texttt{KafkaEntityTelemetryPublisher} (producer) and the GUI's consumer.

\textbf{System health checks.} There is currently no endpoint or signal that reports whether a
backend node, or the cluster as a whole, is actually healthy: \texttt{SimulationControlRoutes}
only exposes per-simulation status (\cref{implementation}), and neither \texttt{ActorMain} nor
\texttt{ClusterMain} subscribes to Pekko Cluster's own membership events, so a node joining, leaving, or being marked unreachable
by the Split Brain Resolver (\cref{fault-tolerance}) produces no observable signal outside of the
cluster's internal logs. The Caddy gateway of the containerized deployment (\cref{deployment}) only compensates in part:
it notices a dead replica \emph{passively}, after requests to it have failed, and cannot tell a
replica whose process is up but has not yet joined the cluster from a healthy one. Adding the
\texttt{pekko-management} module's cluster-health HTTP routes would give each node a
liveness/readiness probe, which the gateway could poll actively and an external orchestrator
could use to know when a node is safe to route traffic to, or when it should be restarted.
